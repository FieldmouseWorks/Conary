# M6 delivery plan

M6 is the milestone where conaryd runs the landing flow and `steward.py` is
deleted. Its scope and exit check are the M6 row of the
[roadmap](DESIGN.md#12-roadmap), and its slices are listed in
[#256](https://github.com/FieldmouseWorks/Conary/issues/256). This file
records which slices are done, which issue delivers each remaining
requirement, and what each one waits on. Each requirement has exactly one
delivery owner, and finished work is not scheduled again. Reconciled
2026-11-13 against main at `a75e0bf`, the issues linked here, their open PRs,
and remi's main at `e47165e` (remi#1218, which turned the shadow on, with
burrow pinned at `7c727f4`).

The acceptance criteria for each slice, written against the lessons register,
are [#307](https://github.com/FieldmouseWorks/Conary/issues/307)'s. That
issue updates this plan and #256 with the lesson IDs once the register
([#305](https://github.com/FieldmouseWorks/Conary/issues/305)) and its check
([#306](https://github.com/FieldmouseWorks/Conary/issues/306)) are in. This
file doesn't name lesson IDs, and it doesn't redo the Properties work.

## Boundaries

These are #256's boundaries, unchanged. Nothing in this file adds to them.

- Each slice, and each task in one, is its own PR. A child issue grants no
  authority beyond #256.
- Slices 1 to 4 touched nothing live. Slice 5 switches one repository at a
  time, remi first, then every other repository. `steward.py` and the
  landing-flow Python are deleted only after every repository lands through
  conaryd.
- Slice 5 takes burrow#517 (the stage labels) and the
  [proof-queue change](#the-proof-queue-prerequisite) as they are.
- Logic goes in Conary's Rust libraries. No new steward Python, and nothing
  is ported twice ([roadmap](DESIGN.md#12-roadmap), "What gets slotted in").
- Finish-line items 7 (no Nix, no burrow) and 9 (related work pays for one
  gate) are in the [finish line](DESIGN.md#12-roadmap). They hold for every
  task below, and they aren't restated here.
- No task here enables a repository, provisions a key or deletes a live path
  unless its own issue says it does. Even then it goes through the machine's
  normal deployment process. Producer private keys are secrets and stay with
  the machine's owner.
- The cutover makes one change the owner will see: an R2 or owner call is
  approved with a GitHub review that carries the flow's marker
  ([flow.md](flow.md#person-approval)).

## The proof-queue prerequisite

The prerequisite is
[burrow#518](https://github.com/FieldmouseWorks/burrow/pull/518), "autoland:
hold a proof slot only while the check's own derivations build". It was merged
2026-11-08 as burrow `0dbfe0a`. It's an ancestor of the burrow remi runs
(`ff6f622`, deployed 2026-11-12), so it's live. With it, a proof's inputs build
outside the proof line, in a machine heavy slot. The slot is held only while
the check's own derivations build. A prebuild belongs to one head and one
proof, and it stops when either one changes.

Slice 5 takes it as it is. The Rust proof plugin keeps that split: preparation
happens outside the scarce proof capacity, and the proof itself is a program.
[m6-plugins.md](m6-plugins.md) plans that (tasks C3 and P).
