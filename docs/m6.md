# M6 delivery plan

M6 is the milestone where conaryd runs the landing flow and `steward.py` is
deleted. Its scope and exit check are the M6 row of the
[roadmap](DESIGN.md#12-roadmap), and its slices are listed in
[#256](https://github.com/FieldmouseWorks/Conary/issues/256). This file
records which slices are done, which issue delivers each remaining
requirement, and what each one waits on. Each requirement has exactly one
delivery owner, and finished work is not scheduled again. Reconciled
2026-11-14 against main at `4951bdd`, #256's slice-completion comments and
the issues linked here.

Each remaining task is held to the lessons register's entries
([lessons.toml](lessons.toml)), as
[Lessons each task is held to](#lessons-each-task-is-held-to) says. What a
lesson is, and who delivers it, is DESIGN's
[Properties](DESIGN.md#properties) index; this file doesn't restate it.

## Boundaries

These are #256's boundaries, unchanged. Nothing in this file adds to them.

- Each slice, and each task in one, is its own PR. A child issue grants no
  authority beyond #256.
- Slices 1 to 4 touched nothing live. Slice 5 switches one repository at a
  time, remi first, then every other repository. `steward.py` and the
  landing-flow Python are deleted only after every repository lands through
  conaryd.
- Slice 5 takes burrow#517 (the stage labels) and the
  [proof-queue change](#the-proof-queue-prerequisite) as they are.
- Logic goes in Conary's Rust libraries. No new steward Python, and nothing
  is ported twice ([roadmap](DESIGN.md#12-roadmap), "What gets slotted in").
- Finish-line items 7 (no Nix, no burrow) and 9 (related work pays for one
  gate) are in the [finish line](DESIGN.md#12-roadmap). They hold for every
  task below, and they aren't restated here.
- No task here enables a repository, provisions a key or deletes a live path
  unless its own issue says it does. Even then it goes through the machine's
  normal deployment process. Producer private keys are secrets and stay with
  the machine's owner.
- The cutover makes one change the owner will see: an R2 or owner call is
  approved with a GitHub review that carries the flow's marker
  ([flow.md](flow.md#person-approval)).

## The proof-queue prerequisite

The prerequisite is
[burrow#518](https://github.com/FieldmouseWorks/burrow/pull/518), "autoland:
hold a proof slot only while the check's own derivations build". It was merged
2026-11-08 as burrow `0dbfe0a`. It's an ancestor of the burrow remi runs
(`ff6f622`, deployed 2026-11-12), so it's live. With it, a proof's inputs build
outside the proof line, in a machine heavy slot. The slot is held only while
the check's own derivations build. A prebuild belongs to one head and one
proof, and it stops when either one changes.

Slice 5 takes it as it is. The Rust proof plugin keeps that split: preparation
happens outside the scarce proof capacity, and the proof itself is a program.
[m6-plugins.md](m6-plugins.md) plans that (tasks C3 and P).

### What M6 doesn't port

Five of the steward's habits are forbidden by an entry in the register.
None of them survives the cutover:
[#314](https://github.com/FieldmouseWorks/Conary/issues/314) doesn't switch
remi, and no group of
[#315](https://github.com/FieldmouseWorks/Conary/issues/315) switches, while
conaryd's flow still does one. These five are cutover prerequisites;
[#312](https://github.com/FieldmouseWorks/Conary/issues/312) names any
others.

1. **A proof run by a model** (`no-model-in-mechanical-step`). The flow
   sends a `Job` recipe to no proof plugin (C3), and the proof plugin
   refuses one and declares no model (P). A repository whose proofs include
   a model-run check, as wend's `proofJobs` does, doesn't cut over with it:
   it becomes a program first ([S2e](m6-cutover.md#s2e-wend), #315's
   decision).
2. **A binary first-priority queue** (`explicit-priority`). Admission and
   proof slots go by an explicit priority level, then age. The order
   [flow.md](flow.md) gives proof slots today, queued first-priority PRs
   first, is replaced by a task #312 files, not carried across. No task
   before it adds another reader of `first` for order. The `first` label may
   map to a level; it isn't the order.
3. **A silent fallback** (`degraded-counts-as-failed`). A fallback taken, a
   lookup that half-worked or a record read conservatively is recorded as
   an op naming what degraded, counts as its check's failure, and shows in
   the flow's status. An evidence lookup that can't verify is no reuse
   ([gate-reuse.md](gate-reuse.md)), and the gate runs.
4. **A switch that waits on a deployment** (`off-switch-independent`,
   `live-settings`). A pause, a hold and a repository's landing owner are
   settings read at the next decision (#312, #313). Turning work off, or
   handing a repository back to the steward, needs no pass, CI run, merge
   or deploy. Installing a plugin or a producer's key is a deployment, an
   exception the settings schema declares; the switches aren't.
5. **Paused work that keeps its capacity** (`pause-vacates`). A pause or a
   hold frees at once every slot, lane and proof its work holds, cancelling
   the plugin and producer work it started, and keeps the branch, PR and
   flow state (#312, #313). M6 slice 5c's plugins and producers answer that
   cancellation ([m6-plugins.md](m6-plugins.md#restart-and-cancellation)).
